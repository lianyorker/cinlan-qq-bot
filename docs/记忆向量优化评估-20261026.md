## 一、记忆/向量：发现的稳定性与持久化问题

### 问题 A（严重）：召回在写锁下逐条同步远程调用

**证据**：
- `chatprefs/store.go:906,914` RecallFacts 对 `e.Facts`(≤40) + `e.Archive`(≤400) 逐条调 `scoreFactHybrid`
- `chatprefs/store.go:614-620` scoreFactHybrid 内，remote enabled 时每条 fact 单独 `vec.Similarity`，内含 2 次 `RemoteVector`，各 1.5s 超时
- `chatprefs/store.go:942` RecallFacts 末尾 `saveLocked`，所以**整个遍历持的是写锁 `s.mu.Lock()`**（见函数入口）

**后果**：远程 embedding 冷缓存时，最坏一次召回 = 440 条 × 2 次 HTTP × 1.5s 超时，全程占用 chatprefs 写锁。
期间所有聊天的 mood 读写、fact 增删、印象查询全部阻塞 → 整个 bot 卡死。

**现有缓解**：vecstore 有 SHA-256 磁盘缓存（`vecstore.go:210-245`），命中则 0 网络。但首次/新文本必走网络。

### 问题 B（中）：每次写操作全量重写整个 store 文件

**证据**：`chatprefs/store.go:1371-1391` saveLocked 全量 `MarshalIndent(所有 Chats+Profiles+Cards)` → 写 `.tmp` → `Rename`。
调用点密集：BumpMood、RecallFacts、AddFact、每条消息都可能触发。

**后果**：聊天数量多后，每条消息都在全量序列化+整文件重写，写放大随数据量线性增长。SSD 寿命 + IO 毛刺。

### 问题 C（低）：远程向量维度无一致性校验

**证据**：`vecstore.go:122` 只校验 `len(ra)==len(rb)`，不校验与历史缓存维度一致。
换 embedding 模型（维度变化）时，`loadCache` 仅按 `p.Model != cfg.Model` 整体丢弃（`vecstore.go:354`）——模型名相同但维度变了的情况不防。低概率，但换模型需手动清缓存。

### 问题 D（低）：缓存淘汰是随机删除

**证据**：`vecstore.go:226-236` 缓存满 6000 时随机删 10%。
随机淘汰可能删掉高频 fact 的向量，使其下次召回又走网络。非 LRU，不最优但可接受。

## 二、优化方案（按投入产出排序，先不写码）

### 方案 1：召回热路径移出写锁 + 向量旁路（解决 A，最高优先）

**最小改法**：
1. RecallFacts 分两段：读锁下算分排序（纯 bigram + 概念，不碰远程）→ 释放锁 → 选中项的 LastSeenAt/Weight 更新用一次短写锁批量回写。
2. **远程向量从召回热路径剥离**：召回只用本地（bigram + ConceptOverlap，均零 IO）。
   远程 dense 相似度改为 reflect 后台预计算，结果缓存，热路径只读缓存命中值。
3. 给 scoreFactHybrid 的 remote 分支加全局超时预算（如整次召回最多花 200ms 在向量上，超了就降级纯本地）。

**收益**：召回从"最坏秒级持锁"降到"亚毫秒无 IO"。向量语义能力保留，只是不再实时阻塞。
**风险**：低。本地 bigram+概念已是召回主力，远程只是加分项（`sim>=0.45` 才 +分）。

### 方案 2：持久化去抖 + 脏标记（解决 B）

**最小改法**：
- saveLocked 不立即落盘，置 dirty 标记；后台 ticker（如每 5-10s）或 N 次写累计后 flush 一次。
- 进程退出 / SIGTERM 时强制 flush（避免丢数据）。
- 参考 vecstore 已有的 `dirty` 计数模式（`vecstore.go:238-242` 攒 8 次才存）——chatprefs 照搬。

**收益**：写放大从"每条消息一次全量"降到"每 5-10s 一次"。
**风险**：中。崩溃窗口内最多丢几秒的 mood/fact 增量。需加退出 flush 兜底。

### 方案 3：向量维度校验（解决 C，顺手）

loadCache 时记录向量维度，与首个远程响应比对，不一致则丢缓存并告警。改动 10 行内。

### 方案 4（可选）：缓存淘汰改近似 LRU（解决 D）

给 cache value 加 lastHit 时间戳，淘汰时删最旧 10% 而非随机。收益有限，优先级最低。

## 三、"更稳更持久"的整体判断

当前记忆/向量**功能完整、设计不差**（双引擎、磁盘缓存、原子写、质量门俱全），
真正的稳定性短板是**两处热路径耦合**：

- 召回把远程 IO 压在写锁里（问题 A）→ 偶发卡死，这是"稳"的最大威胁
- 每写全量重刷文件（问题 B）→ 长期写放大，这是"持久"的最大威胁

**建议执行顺序**：方案 1 → 方案 2 → 方案 3 →（方案 4 看情况）。
方案 1、2 做完，"更稳更持久"的核心诉求即达成。

## 五、附录：方案 1 / 方案 2 详细改法（待实施，先不写码）

> 两方案相互独立，可分开提交。建议先 1（解决卡死=稳）后 2（解决写放大=持久）。
> 均属 L3（热路径 + 并发 + 持久化），实施时每步配并发测试，别一次改完。

### 方案 1：召回热路径移出写锁 + 向量旁路（问题 A）

**当前结构（已核实）**：
- `RecallFacts`(store.go:887-945) 全程持**写锁** `s.mu.Lock()`，因为它要：① 遍历 ≤440 条逐条 `scoreFactHybrid`(:906,914)；② 命中项回写 `Weight+=0.25`、`LastSeenAt=now`(:933-939)；③ 末尾 `saveLocked`(:942)
- `scoreFactHybrid`(:609-623) remote enabled 时**每条 fact** 开 1.5s ctx 调 `vec.Similarity`(:614-620)，内含 2 次 `RemoteVector`

**步骤 1.1 锁降级——算分读锁、回写短写锁**，把 RecallFacts 拆三段：
1. 读锁下快照候选：改用 `lookup`（非 `entry`，读锁下不创建条目），拷出 Facts/Archive 快照 + 原始 idx + `grams`，然后 `RUnlock`
2. 无锁算分排序 → 取 top limit → 得选中项 (idx, archived)
3. 短写锁批量回写 Weight/LastSeenAt + 一次 saveLocked
- **关键陷阱**：第 1 段释放锁后，第 3 段重新拿锁时 Facts 可能已被 AddFact/合并改动。第 3 段回写前**按 Text 重新定位**（不信旧 idx），对不上就跳过该条回写（召回结果照返回，仅热度不涨，可接受）

**步骤 1.2 向量移出热路径（核心）**：
- `scoreFactHybrid` 远程分支(:614-620) 从召回删除；召回只保留零 IO 两项：`scoreFact`(bigram) + `ConceptOverlap`(概念簇，纯内存)
- 做法：加 `allowRemote bool` 参数，召回传 false；或新增 `scoreFactLocalOnly`
- 若仍要 dense 加分：**只查 vecstore 缓存**(`e.cache[key]`,:213)，命中才用，未命中不发网络、不等待

**步骤 1.3（可选，保留 dense）**：reflect sweep(engine.go:113) 里对各 chat 活跃 facts 批量 `RemoteVector` 预热缓存，使 1.2 的"只读命中"大概率命中。嫌复杂可只做 1.1+1.2，砍掉召回期所有远程调用——本地 bigram+概念已是召回主力，远程仅 `sim>=0.45` 才 +分且封顶 +6，影响有限。

**风险/验证**：风险低-中，主要在 1.1 两段式锁（靠 Text 重定位解决数据变动）。验证：现有召回测试 + 新增并发测试（召回时并发 AddFact，断言不 panic、不写坏）。收益：召回从"最坏 440×2×1.5s 持写锁"→"亚毫秒无 IO 读锁"。

### 方案 2：持久化去抖 + 脏标记（问题 B）

**当前结构（已核实）**：
- `saveLocked`(:1371-1391) 每次全量 `MarshalIndent(所有 Chats+Profiles+Cards)` → 写 `.tmp` → `Rename`
- 调用点：BumpMood、RecallFacts、AddFact 等几乎每条消息触发
- chatprefs **当前无 Close/Flush、无后台 goroutine**（故当前崩溃不丢数据，因每次立即落盘）
- 对照：vecstore 已有 `Flush()`，main.go:776 `defer vecEngine.Flush()` 收尾；可照搬其 `dirty>=8` 去抖模式(vecstore.go:238-242)

**步骤 2.1** Store 加字段：`dirty bool`、`saveCh chan struct{}`（缓冲 1）、`closed chan struct{}`

**步骤 2.2** saveLocked 改为只置脏 + 非阻塞通知，不立即写：
- 原落盘逻辑抽成 `flushLocked`（真正写盘）
- 新 saveLocked：`s.dirty=true; select { case s.saveCh<-struct{}{}: default: }`
- 所有现有调用点签名不变，行为变"标脏"

**步骤 2.3** 后台 flush goroutine（去抖）在 Load 成功后启动：ticker 5s，`<-ticker.C` 时 `if dirty { flushLocked; dirty=false }`（持锁）；`<-closed` 时最后 flush 一次再 return。可选：攒够 N 次写（如 20）立即 flush 不等 ticker。

**步骤 2.4** 加 `Close()`（必须，防丢数据）：`close(s.closed)` + 等后台完成最后 flush（WaitGroup 或再同步 flush 一次）。main.go 在 vecEngine.Flush 旁加 `defer chatPrefs.Close()`（需把 local_extensions.go:43 Load 的 store 传到 main 的 defer 作用域）。

**风险/验证**：
- 风险中。核心：硬 `kill -9` 丢去抖窗口内（≤5s）的 mood/fact 增量。缓解：退出 flush 兜底覆盖正常退出；硬 kill 只丢最近几秒（非历史），对记忆场景可接受
- 次要：后台 goroutine 与 `s.mu` 交互，flushLocked 须持锁调用，别与 saveLocked 锁打架（saveLocked 只置脏不碰锁）
- 验证：① 现有 `Load` 后立即读用例仍过（去抖不影响内存态）；② 写后不等 ticker 直接 Close，断言已落盘且内容正确；③ 空 path（`chatprefs.Load("")`，多处测试用）时 goroutine 不启动或 flush 空转
- 收益：写放大从"每条消息一次全量"→"每 5s 最多一次"，数据量越大收益越明显

**简化替代（嫌 goroutine 复杂）**：纯计数去抖——saveLocked 累计次数，每 N 次或距上次超 T 秒才真落盘，其余标脏；退出时 main.go 强制 flush 一次。少一个 goroutine+channel，但"长时间低频写"场景落盘会拖到下次写触发（活跃 bot 影响不大）。
