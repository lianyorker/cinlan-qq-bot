# Cinlan QQ Bot 完整性审计

本报告覆盖本轮对 Go Agent runtime、QQNT native runtime、OneBot 兼容层、配置扩展和回复决策的检查。结论区分“代码已实现”“交叉编译已验证”和“真实环境尚未验证”。管理台 UI 已移除，运维只依赖 cmd 窗口日志和 Bearer 保护的 Admin API。

## 结论摘要

- Windows：核心 Go bot 可运行；QQNT native loader、hook、Node runtime 只支持 Windows 10/11 x64。
- Linux：核心 Go bot 可运行，支持通过外部 OneBot 11 服务接入 QQ；不支持官方 QQNT 注入、loader、hook 或自动登录。linux/amd64 与 linux/arm64 交叉构建已通过。
- 自定义扩展：Provider、Persona、Tool、Skill、Knowledge、MCP、Webhook、Subagent 和 Go registry 均有扩展入口；Tool/Skill/Knowledge/MCP 资源有 Binding 隔离。Command、Plugin/Webhook 当前仍是进程级注册，不能仅靠 Binding 做精确授权。
- 自主回复：已增加 Binding 级 reply_policy。群聊和私聊都支持 disabled、mention_only、always、ai_decide；旧 smart_attention 和 require_mention 配置继续兼容。
- 管理 UI：Web 管理台（`/admin/` 页面、登录会话、`/api/v1/chat`）已移除；运维只依赖 cmd 窗口日志与 Bearer 保护的 `/api/v1/*` Admin API。

## 本轮已完成

### 回复策略

reply_policy.mode=ai_decide 的处理顺序为：Binding 匹配 -> 通用确定性过滤 -> 独立 Attention Provider 调用 -> 严格 JSON/置信度校验 -> 正式回答。路由器不会回答用户，也不会获得 Tool 权限。

默认保护：

- 路由历史为 none。
- 路由请求不携带 QQ user/chat/self ID、昵称、原始消息 ID、完整回答 Persona prompt 或消息组件。
- 请求 ID 和维护会话 ID 使用哈希值。
- 失败和低置信度默认 ignore；可按 Binding 配置 reply 或 mention_only。
- BOT_ATTENTION_TIMEOUT、BOT_ATTENTION_RATE_LIMIT、BOT_ATTENTION_RATE_WINDOW 独立控制超时和每用户预算。
- routing_scope 与正式 system_prompt 分离，业务范围不再依赖代码中的技术词和生图/代码关键词。

示例见 examples/chat-bindings.json 和 examples/personas.json。契约见 docs/自定义AgentAPI.md。

### 扩展安全

Subagent 已增加 inherit_history 和 history_limit，默认不复制主会话历史；跨 Provider 仍需由部署者确认数据驻留。Provider override 已按实际实现写入 docs/子Agent.md。

### 平台发布

发布脚本现在生成：

- windows-amd64：Go bot + QQNT loader + hook + native runtime。
- linux-amd64、linux-arm64：纯 Go OneBot 包。
- darwin-amd64、darwin-arm64：纯 Go OneBot 包。

Dockerfile 默认 QQ_PLATFORM=onebot 并监听 :8080，与健康检查端口一致。

## 仍存在的高优先级问题

### H1: Admin API 仅限可信运维调用

当前通用 API 的部分响应包含完整本地路径、Persona system prompt、开场对话、原始 session scope 和知识片段，POST /api/v1/actions 具有直接操作能力。Web 管理台已移除，`/api/v1/*` 仅保留 Bearer token 保护；部署时必须设置 `ADMIN_API_TOKEN`，且 `HTTP_LISTEN_ADDR` 应保持 loopback 或受控网络。

### H1: Webhook 是全局事件出口

Event webhook 在 wake、白名单和 Binding 判断前接收平台事件；HTTP URL 允许非 TLS 地址，当前没有 Binding scope、字段裁剪或明确的网络策略。生产部署不应把它当作群/个人隔离扩展。建议增加事件类型、Binding scope、payload 字段白名单、HTTPS/loopback 限制和默认 fail-closed，并为旧配置提供迁移告警。

### H2: Command、Plugin 不是 Binding 级资源

Tool、Skill、Knowledge、MCP 有资源快照隔离，但 Command 和 Plugin registry 是全局的。需要按群或个人授权时，应在扩展内部检查 scope.binding_name，或将能力迁移为显式授权 Tool。

### H2: native 运行时对 QQNT 版本敏感

loader/hook 的真实兼容性依赖官方 QQNT build。每次 QQ 更新都必须重新验证签名、IAT、wrapper/session attach 和消息闭环；不能仅凭 Go 交叉编译结果宣称 native 可用。

### H2: 默认权限仍需部署审查

Subagent 和 Command 的历史默认权限偏宽，Webhook 默认 fail-open，Admin 示例仍使用占位凭据。生产配置必须显式设置强凭据、最小权限、白名单和 TLS；配置验证 API 实现前不要把这些值展示给 UI。

### H3: 构建与发布缺少 CI

当前验证依赖本地 PowerShell、Go、Rust 和 Node。应在 CI 中固定执行 Go test/vet、Windows native Rust build、Linux cross-build、Node tests、公开发布扫描和包内容检查，并锁定基础镜像与第三方 OneBot 镜像版本。

## 推荐上线顺序

1. 用真实群和私聊各做一轮白名单端到端测试，确认 native 与 OneBot 的消息、引用、图片和失败回退。
2. 给 Attention 使用单独的低成本、可信 Provider，并监控 decision、ignore、error、budget 指标。
3. 为 Webhook、Command、Plugin 增加作用域与字段最小化，再允许业务扩展接收非命令消息。
4. 实现脱敏 Admin API 和配置验证 API，之后才接入 UI 原型。
5. 建立 Windows/Linux CI 和可复现发布包，最后再考虑默认开启更多主动能力。
